# 累计钱包与每日三批香火交易

状态：独立开发候选，已作专用隔离演练，尚未公开部署或发布。社区用量仍是 Host 申报的软信任，不能宣称已验证 Token 真实性。

## 冻结规则

- 在线资产由 Linux Backend 的 SQLite 钱包与流水唯一记账。本地仅缓存，不能导入自报余额。
- 只有首次使用累计协议后，可用、冻结和已到账收益才跨日保留；今日凝香、今日上香、梁小号与每日梁案继续按业务日期统计。
- 每日符合资格时赠 10 炷，不补领未访问的旧日；同设备同业务日不重复领取。
- 启用累计协议后，不足一炷的已入账 Token 余量跨日保留，按相同模型权重累积；交易收益不冒充 Token 用量。
- 未升级身份的余额及不足一炷进度按业务日过期；升级只保留服务端确认的启用当日未用余额和余量，并保留已入账水位，绝不补发历史失效余额。
- 钱包总额 = 可用 + 冻结；预计收益不计入余额。投票与投入在同一事务中检查可用余额。
- 离线账本保持隔离，不进入社区交易、不合并钱包或历史。

## 业务时区内的固定日程

以下为新建场次的 `liangxiang-market-v3` 日程；三批均可投入四小时，时点在开场时持久保存，重启或升级不重算。

| 批次 | 可投入/修改/撤回 | 只上香立线 | 官方参考点 |
| --- | --- | --- | --- |
| 早盘 | 07:00–11:00 | 11:00–12:00 | 12:00 |
| 午盘 | 12:00–16:00 | 16:00–17:00 | 17:00 |
| 晚盘 | 17:00–21:00 | 21:00–22:00 | 22:00 |

22:00 后三个参考点均固定，23:00 进入收官倒计时，24:00 封存旧梁案收盘值并结算。服务端先推进所有到期边界，再允许新投票改变原始计数；换日不得先读取新梁案作为旧场收盘值。

已存在的v2场次仍从09:00开始早盘，其他两批同上；v1场次保留原日程：投入段为09:00–11:00、12:00–17:00、18:00–20:00，封盘11:00/17:00/20:00，定线12:00/18:00/21:00，同样午夜结算。升级不能改写已开场时点或将旧回执改标v3；下一业务日新场次才采用新规则。

同一身份每批一个方向、一个汇总仓位。投入先冻结；封盘前可设置整个目标仓位或以零金额撤回。封盘后方向与金额不能改变；后续批次可独立换向，但不能分走旧批奖池。待定参考点不显示盈亏。

每批均以同一收盘点与本批参考点比较：收盘高则多方赢，低则空方赢，相同退款。用原始票数交叉相乘精确比较，不能使用界面六位截断值。赢家按本批投入比例分输家本金；整数商先分，余香按最大余数补齐，同余按本批首次入场顺序。

单边池、无票或 0%/100% 参考点取消退款。中途换案导致不可比时取消尚未结算场次并退款。订单和结算都有持久幂等回执；重启或跨日补结使用原场次，不延长截止时间，不猜测历史参考点。

定线前多方偏好压低参考值、空方偏好抬高；定线后目标翻转。组织投票与跨批对冲是玩法的一部分，不宣传完全防控盘或每种组合都必有亏损风险。原自动上香方向不会根据仓位偷偷切换。

## 传输与容量边界

- 首次打开只读取当前场次、本人钱包与当天公共分钟 K 线：每页最多288根，按游标读取，最长夏令时业务日不超过1500根；个人回执默认20条、每页最多50条。旧五分钟数据保留其真实粒度，不拆成虚构分钟。
- 图表历史按需读取，日常 SSE 不携带全历史数组；私人仓位/余额只向本人连接发送。
- 本地缓存最多2MiB，公共行情保留最近七个缓存梁案日（每块最多1,500根，非七天TTL），个人回执最多三十份；超额淘汰缓存，不影响资产。
- 后台保存最小仓位、流水、结算回执与官方 P1/P2/P3/Pc；动画轨迹、截图和私人复盘样式不上传。
- 本机 Host 主动建立一条云端 SSE；上香和投入使用签名 HTTP。浏览器复用现有本机 SSE。
- 公共变化最多每秒合并一帧，心跳 25 秒；慢连接采用有界缓冲与重连快照，不无限积压。
- 动画/静态为本地偏好，默认尊重减少动态设置；隐藏或关闭窗口时停止装饰动画。

目标配置为 2 CPU / 4 GiB；并发、封盘写入、午夜结算和重连洪峰必须在目标资源下验证。安装包、首开接口体积和缓存上限应使用构建与接口实测记录，不能由源码大小推断。

## 安全与恢复

### 旧版过渡

新版Host用`x-liangxiang-wallet: cumulative-v1`启用累计协议。旧日账身份继续每日凝香、夯拉、梁祠和赠香，余额与零碎Token按日过期；后台升级不会为这些身份积累隐藏余额。第一次累计协议请求仅保留当天实际余量，启用不可逆。

同一身份启用钱包后再用旧协议，后端在修改个人账本前返回`wallet_upgrade_required`与最低客户端版本2.0.0；可用、冻结、参考点及结算不受影响。支持该码的客户端显示明确升级提示。已发布1.2.0忽略服务端说明，需要客户端提示补丁或升级2.0才会改变显示，不能靠后台文案假装解决。完整矩阵及证据见[`LEGACY_WALLET_COMPAT.md`](LEGACY_WALLET_COMPAT.md)。schema15持久记录启用点；原候选钱包保留已有累计资产，原日账不回补历史。

HTTPS 保护传输；现有 Ed25519 签名证明安装密钥持有与请求完整性。它不能证明本机申报的 Token 真实。客户端嵌入统一密钥也不能消除这条边界。

身份密钥是长期钱包的访问凭据。重装不删除服务端余额；恢复必须证明持有凭据，不能仅凭设备指纹取回。钱包切换上线需校验旧客户端兼容，不得并行维护两套可花余额。

原始资金流水追加保存，纠错使用补偿流水；定期进行一致性备份并验证恢复。服务器结算不依赖客户端在线或本地图表刷新。

`LIANGXIANG_TOKEN_PER_INCENSE` 必须与持久钱包及当前梁案的阈值一致。存在旧钱包时直接更改该配置会在服务构造阶段明确拒绝启动，不会等到用户领取赠香后才失败，也不会自动重估资产或余量。更改阈值需要独立、经验证的钱包迁移；默认 50,000 保持不变。

每场持久保存 `rule_version`，新回执记录该场的原始规则版本，不从当前客户端常量补写历史。当前实现同时识别v1、v2与v3，结算使用该场保存的时点；日程调整不需要数据库或缓存迁移。schema 13 为此前仅实现 v1 的 schema 12 候选库补列并固定回填 `liangxiang-market-v1`；旧回执缺少版本时保持缺省，不伪造元数据。未知的未结规则会在启动时拒绝，运行中出现未知版本也拒绝推进、押仓、退款或派彩，保留资金与原始记录等待兼容实现，不能静默按当前规则处理。

分钟行情候选使用 schema 14 的独立分钟表，原五分钟表保留只读；两种粒度不会混写。全天00:00–24:00均可记录梁位；投入时段只约束仓位，以顶部细带标注，真实业务时钟之后用独立浅灰待开梁区显示，不能补造未来数据或历史缺口。分钟桶全局共享，不按用户新建数据或新增轮询；本地行情与回执缓存总量上限2MiB。
