# 钱包升级与旧版兼容

范围：2.0开发候选（schema15）与正式1.2协议；尚未部署生产。旧版支持不设置自动失效日期。

## 兼容矩阵

| 客户端／身份 | 行为 | 资金规则 |
| --- | --- | --- |
| 从未启用累计协议的旧1.2身份 | 继续凝香、夯／拉、梁祠及当日赠香 | 每个业务日余额及不足一炷的进度过期；不为未来升级积攒历史余额 |
| 首次使用累计协议 | 原身份只启用一次钱包 | 只保留启用当日的真实余香及进度；不重新赠香、不加总历史日账 |
| 已启用钱包，再用旧协议 | 个人读写返回412 `wallet_upgrade_required`，最低版本2.0.0 | 在修改日账、领取新赠香或提交用量前拦截；不清余额、不释放冻结、不改仓位与结算 |
| 新客户端 → 旧1.2后台 | 基础凝香、上香、梁祠可用 | 仍为日账；市场未开放，不承诺累计资产 |

累计启用点是服务端持久字段`cumulative_since`，不可由后续旧请求反向关闭。
尚未升级的人不因后台升级被强制升级；已经启用新钱包的人须继续使用支持钱包的客户端。
这是明确的单向升级契约，不再以当天余额偶然可被旧公式表示作为是否允许降级的条件。

**提示显示有二进制边界。** 正式1.2.0的HTTP客户端会忽略服务端`error.message`，
Host只显示HTTP状态；服务器不能远程给其增加文案处理。本候选与另行准备的
`1.2.1-compat.1`旧版提示补丁识别该错误码，显示`请升级至梁相2.0.0及以上版本`，
并锁住上香，不把它写成普通网络故障。补丁基于正式1.2，不加入钱包或梁股，尚未发布。
未安装补丁的1.2.0仍有显示限制，不能宣称已通过后台单独解决。
服务端仍返回中文说明及`min_client_version: "2.0.0"`；协议错误不会造成个人资金变化。

未发布的alpha8市场客户端只识别v1/v2，不认识新v3交易日程；参与v3新场需安装alpha9。
alpha9仍读取已保存的v1/v2场次及回执，不改其冻结资金或时点。这一候选市场兼容边界
不等于强制正式1.2用户升级：1.2没有市场，基础接口仍按上表过渡。

## 单一账本与能力协商

新Host在HTTP及SSE发送`x-liangxiang-wallet: cumulative-v1`，与梁子展示策略头独立。
只有认证后的个人/市场请求才能启用累计协议；能力头不是认证、权限或防伪凭证。
无该值或未知值的日账身份，个人响应继续使用真实日账：

```text
claimed = 实际当日已入账Token
earned = floor(claimed / token_per_incense)
used = 实际当日接受的上香数量
remaining = earned - used
remainder = claimed % token_per_incense
```

日账的过期同时清除可用余额和零碎Token进度，负金额追加`daily_expiry`流水，
保留历史用量与已接受上香记录供梁祠和审计。换日tick、重新启动及迟到首次访问均覆盖；
没有访问的旧日不补赠香。启用当日的已用量、赠香凭证及申报水位保持不变。
激活事务失败全部回滚，不得留下半启用状态。新旧始终只有一份可花余额。

schema15为既有schema12–14候选钱包保留已启用状态，金额、余量、冻结、仓位、回执与
时点均不重算。正式旧日账库没有钱包行，不属于这个保留分支；迁移时不能把内测候选库
当正式库导入。过期逻辑遇到异常的日账冻结资产会明确拒绝，不会清零或放行资金。

重复tick/回执、schema14原资金保留与激活失败回滚。用SQL独立核对资金流水、完整性及外键。

演练记录不能代替本次schema15及启用规则验收。
