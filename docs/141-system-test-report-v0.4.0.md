# 141 — 梁相 v0.4.0 系统全面测试报告（历史基线）

> 测试对象：`v0.4.0`，代码基线 `bb7f8f3`  
> 执行时间：2026-08-17（Europe/London）；服务业务日为 2026-08-18（Asia/Shanghai）  
> 范围：功能、领域不变量、梁祠、Host/DSH 集成、并发与幂等、持久化与恢复、可靠性、可用性、打包与发布门禁  
> 结论：**本地 RC 功能通过；对外发布为“有条件通过”；VERIFIED_PRODUCTION 仍不可发布。**

## 1. 执行摘要

梁祠展示方案及当前主流程已经通过自动化、独立后端压力、双进程并发、崩溃恢复、真实 DSH WebUI、干净 profile 安装和在线链路冒烟。测试没有发现数据错账、重复扣香、超额投票、历史加权错误、今日误入历史、历史故障拖垮今日投票，或重启后数据丢失。

发布前仍有以下门禁：

1. **P0（既有结构性限制）**：当前身份与 Token 权威仍是 community/soft-trust，不能声称 VERIFIED_PRODUCTION。
2. **P1（可用性）**：投票限流表在 60 秒窗口内没有全局硬上限；大量一次性安装标识可造成攻击者可控的短时内存和全表扫描开销。
3. **P1（可用性）**：每次幂等重放、业务拒票和 429 都写一条 info 日志，重试风暴或攻击会造成日志放大。
4. **P1（运维门禁）**：社区服务器 `VERSION` 为 `c2da2e6`，未与受测代码 `bb7f8f3` 对齐。服务器上的后端实现与当前提交之间没有后端源码差异，且实机梁祠可用；但版本门禁仍是红色，不能宣称服务器已部署当前 RC。

因此建议：本地/开发/社区 soft-trust 试用可以继续；对外放量前先修复两项 P1 可用性问题，并通过标准部署脚本使服务器版本与发布提交一致。

## 5. 后端正确性与可靠性

### 5.1 单进程原子性

在全新文件数据库上预置仅 1 炷可用香火，同时发送 200 个不同 `request_id`：

- 接受：1；
- 拒绝：199；
- 没有超额扣减；
- 完成耗时：55.0 ms。

随后对同一个 `request_id` 并发发送 100 次：

- 100 个响应都返回同一个已接受业务结果；
- 99 个标记为 replay；
- 账本只增加 1 票、只消耗 1 炷；
- 完成耗时：16.9 ms。

同一 `request_id` 改投相反方向返回 HTTP 409 `idempotency_conflict`。

### 5.2 双进程共享 SQLite

两个独立后端进程同时连接同一个 SQLite 文件：

- 100 个不同请求争抢最后 1 炷：接受 1、拒绝 99；
- 100 个相同 ID 分散到两个进程：全部得到同一已接受结果，99 个 replay；
- 两个端点最终一致：`used=2`、`remaining=1`、`total=2`、`sequence=3`。

这证明当前 SQLite 事务可承受本机双进程竞争。它不是多机共享文件系统或长期高并发集群证明。

### 5.3 重启与崩溃恢复

对同一文件库执行：

1. 正常优雅停止并重启；
2. `SIGKILL` 强制终止并重启。

两次恢复后均保持 `used=2`、`remaining=3`、`total=2`、`unique_voters=1`。SQLite 检查结果：

- `PRAGMA integrity_check = ok`；
- `journal_mode = wal`；
- `user_version = 4`。

### 5.4 错误隔离

超大请求体返回 413，错误 history cursor 返回 400，未知路由返回 404；上述错误之后 `/v1/health` 仍为 200。没有出现连接进程退出、数据库损坏或今日主流程失效。

## 7. 可用性与负载

### 7.1 公开读短压

单个本地后端累计完成 160,000 次 health/snapshot/history 公开读取：

- HTTP 成功：160,000 / 160,000；
- 吞吐：各批约 14,000–18,500 req/s；
- 进程 RSS：约 61 MB 上升至约 126 MB 后平台化，最后批次没有继续增长；
- 批次结束无残留连接，健康检查持续 200。

另一次 2,000 请求全并发混合读全部成功，整体约 5,755 req/s；在同一突发批次中单请求延迟 p50 176.4 ms、p95 279.5 ms、p99 335.3 ms、max 336.6 ms。

这些数字仅表示同机回环、单节点、短时基线，不代表公网、TLS、反向代理、磁盘抖动或 VPS 容量承诺。

### 7.2 一次性身份洪泛

限流配置为 5 次/分钟时，向全新后端并发发送 12,000 个不同安装标识和请求 ID：

- 12,000 个请求都得到结构化 409，进程没有崩溃；
- 总耗时 1.76 s，健康检查之后仍为 200；
- RSS 从 60.4 MB 上升到 120.8 MB；
- SQLite 主文件约 1.6 MB、WAL 约 4.0 MB。

这不是永久内存泄漏的证明：旧窗口可在 60 秒后由后续投票触发清理。但是 `voteWindows` 只删除已过期窗口，窗口内的全新安装标识没有全局数量上限；超过 1,000 项后，每个后续请求还会扫描整张 Map。攻击者可以在一个窗口内控制内存和 CPU 成本，因此“限流表有界”的现有测试结论过强。

## 8. 发现与修复建议

### P0 — VERIFIED_PRODUCTION 权威链路仍未成立（既有）

**问题**：身份与 Token 资格仍不能由生产服务器独立验证，当前是 community/soft-trust 模式。  
**影响**：不能对外宣称“服务端验证的真实 Token 投票”。  
**建议**：保持 `VERIFIED_PRODUCTION` fail-closed；只有 DSH 提供可验证身份和 Token authority 后，再实现并审计生产适配器。此项与 `docs/BUGFIX.md` 的 BF-001 一致。

### P1 — 投票限流状态在短窗口内无硬上限

**位置**：`src/backend/http.ts:153-179`。  
**问题**：只清除超过 60 秒的窗口，没有限制活跃 installation 数；超过 1,000 项后每次请求扫描全部活跃项。  
**影响**：一次性安装标识洪泛可制造内存增长和 O(n) CPU 扫描，削弱服务可用性。  
**简洁修复**：改成具有硬容量的 TTL/LRU limiter；达到容量时拒绝新 key 或淘汰最旧 key；再增加 IP/入口层全局速率限制。测试必须断言内部容量上限或可观测指标，而不只是“health 仍为 200”。

### P1 — 预期拒票和幂等重放造成日志放大

**位置**：`src/backend/http.ts:537-562`。  
**问题**：每个 429、业务拒绝和 accepted replay 都打印 info 日志。  
**影响**：客户端重试风暴或攻击可以占用 stdout、日志采集和磁盘，并淹没真正异常。  
**简洁修复**：接受的首次投票保留结构化审计日志；replay、香火不足、过期限流改为计数器和采样日志；按原因聚合周期指标，并为日志队列设置背压/轮转。

### P1 — 社区服务器版本未对齐当前 RC

**证据**：`scripts/deploy-check.sh` 返回本地 `bb7f8f3`、服务器 `c2da2e6`。  
**影响**：不能证明社区服务器正在运行本报告受测的完整提交。  
**补充**：`c2da2e6..bb7f8f3` 没有后端源码差异，实际连接的梁祠 API 和 UI 测试通过，因此这不是已观察到的后端功能故障。  
**简洁修复**：发布时只用 `scripts/deploy.sh`，随后运行 `scripts/deploy-check.sh`，要求服务器 `VERSION` 与最终发布提交完全一致。

### P2 — DSH 依赖基线漂移和安装警告

**问题**：仓库钉住 rc.6，干净 profile 安装时部分解析为 rc.7，产生大量 peer dependency 警告；运行时虽通过，但兼容矩阵不再覆盖一个完全整齐的依赖闭包。  
**建议**：选择并统一一个 DSH RC 基线，重新检查 `compat/dsh` 接缝、干净安装和工具调用，再更新 `docs/COMPATIBILITY.md`。

### P2 — 客户端 bundle 偏大

**问题**：`lib/client.js` 914.44 KB，gzip 599.38 KB。  
**影响**：冷加载、低性能设备和 DSH 首屏插件装载成本偏高。  
**建议**：对梁祠日历、图像资源和非首屏逻辑做按需加载；检查重复依赖和 source-map 策略。与 BF-007 一致。

### P2 — 测试总账与实际结果不一致

**问题**：`docs/103-test-matrix.md` 写 392 项/6 个包文件，实际为 396 项/7 个文件；“限流表有界”也缺少容量断言。  
**建议**：从测试输出和 tar 列表自动生成计数；把限流测试改成可观察容量/内存上限测试。

### P3 — 构建配置使用弃用选项

**问题**：tsdown 对 `external`、`noExternal` 发出弃用警告。  
**建议**：按当前 tsdown 配置格式迁移，并对迁移前后 tarball 内容做快照比较。

## 9. 未覆盖或只做了有限覆盖的项目

- 没有公网、TLS、反向代理、真实 VPS 资源限制下的持续压测；
- 没有 24–72 小时 soak、磁盘写满、SQLite I/O 错误、进程管理器反复拉起等故障注入；
- 没有多机共享数据库测试；当前结论只覆盖本机 SQLite 双进程；
- 没有真实 DSH 多会话跨重启、分页/压缩/回放的长时间 Token 对账；
- 独立 UI 实测仅 Chromium 和亮色；没有 Firefox/WebKit、自动 axe、屏幕阅读器和本轮独立暗色复测；
- 没有生产身份/Token authority，因此不能测试或宣称 VERIFIED_PRODUCTION。

## 10. 发布判定

| 场景 | 判定 | 条件 |
|---|---|---|
| 本地开发 / 演示 | **GO** | 明确标注 local/dev |
| 社区 soft-trust 小规模试用 | **CONDITIONAL GO** | 保持软信任声明；监控 RSS、拒票率和日志量 |
| 社区正式放量 | **NO-GO（当前）** | 先修复限流状态上限与日志放大，并对齐服务器 VERSION |
| VERIFIED_PRODUCTION | **BLOCKED** | 等待可验证的 DSH 身份与 Token authority |

修复 P1 后的最小回归集合：完整 `verify`、12k 一次性身份压力、100/200 抢最后一炷、同 ID 双进程重放、16 万公开读短压、崩溃恢复、梁祠 desktop/narrow/keyboard、干净 profile 和在线 smoke。限流回归应新增明确门槛：活跃 key 数不超过硬上限，且超限后的 RSS、p95 和日志量有可审计上界。
